# depop_seller

Semi-automated pipeline for selling second-hand clothes on Depop.
Step 1 (done): sort raw product photos into per-item groups, reviewed by drag and drop.
Step 2 (done): a Sell page whose per-item Depop button opens Depop's listing form with the photos and the description filled in; the human finishes and posts. Descriptions are drafted per item by Claude from photos + a facts line, in the style of `description_style.md`.

## Ownership and commit rules

- Project of GitHub user `doyoungp-dev`, **public** at `github.com/doyoungp-dev/depop_seller` (branch `main`, MIT licence). The history from before publication lives in the private `depop_seller-archive` and never goes public.
- **Everything committed is public - code, docs, tests and commit messages alike.** Nothing personal is ever committed: no photos, no `manifest.csv` (the grouping), no `depop_seller.db`, no `.env`, not the seller's own `description_style.md`, no local paths (a Windows home folder contains a real name), no shop handle, no real listings, no family or friends. All of that lives in the data folder outside the repo (see Data layout). Commit messages describe the software, never whose shop or which batch prompted a change.
- The owner is the **only** author and committer. Never add `Co-Authored-By`, "Generated with Claude", or any AI attribution to commit messages, PR descriptions, or source files. Use the repo-local git identity that is already configured; do not change it.
- Never commit images. `raw_image/`, `sort_image/`, `thumbs/` and the whole `product_image/` tree are gitignored, as is `.claude/` (local Claude Code settings).
- Never commit secrets. `ANTHROPIC_API_KEY` is read from the environment, falling back to `.env` in the data folder (and, for old installs, the app folder). Never read, print, or edit a `.env`; never ask the user to paste a key into chat. Test fixtures use keys that are obviously fake (`sk-ant-test-...`), never the real `sk-ant-api03-` shape, which secret scanners flag.
- **No cloud infrastructure.** Everything runs on the user's own computer (local files, local SQLite). The only network calls are the Anthropic API for photo grouping, Claude Code on the user's subscription for descriptions, and Depop's website in the user's own Chrome. Do not propose or add hosted services, containers or deployment tooling. GitHub Releases are how the app is distributed and updated; that is the one exception, and the app only talks to GitHub when the user presses **Check for updates** or **Update** in Settings - never in the background. No CI: `release` runs the tests locally before anything is published.
- **Releases** are one command: `python -m depop_seller release [X.Y.Z] [--notes ...] [--dry-run]` (`release.py`). It refuses a dirty tree or a branch other than `main`, checks that `gh` is signed in, that `github.com/doyoungp-dev/depop_seller` is public (a private repo's releases are invisible to the app's unauthenticated check) and that this checkout's root commit is the same as `origin/main`'s and a fast-forward of it - **that guard is what keeps the private pre-publication history from ever being pushed to the public repo, even through a tag** - then runs the tests, writes the version into `pyproject.toml`, `depop_seller/__init__.py` and the macOS `Info.plist` and commits `Release X.Y.Z`, builds `dist/DepopSeller.zip` from `git ls-files` only (never whatever else sits in the folder) and checks it with `updates.read_update` exactly as installed apps will, builds the Windows installer around that zip (see **Windows installer**), tags `vX.Y.Z`, pushes `main` and the tag, and runs `gh release create` with both files. Default version: the current one if never released, else the next patch; default notes: the commit subjects since the last release, which the Settings page shows as "What's new" - so write commit subjects for sellers. Every step is re-runnable after a failure. `--dry-run` reports every blocker and builds the zip and the installer but commits and publishes nothing. The asset name is stable, so `releases/latest/download/DepopSeller.zip` in the README always serves the newest. Windows is the supported platform; the macOS launchers exist but are untested.

## Data layout

**Two folders, kept apart** (`config.py`): the **app folder** (`PROJECT_ROOT`) is the software and
holds nothing personal, so it can be replaced or published; the **data folder** (`DATA_DIR`,
`~/DepopSeller`, overridden by `DEPOP_SELLER_DATA` or `data_dir` in the per-machine
`machine_config_file()`) holds everything of the seller's. That split is the whole reason moving to
another computer is one copy - never put seller data back in the app folder.
`migrate_into_data_dir()` moves an older install's `product_image`, `depop_seller.db`,
`description_style.md`, `style_history` and `.env` across once (called from `cli.main`, never
overwrites, a rename when both are on one drive), and `load_api_key` still reads the app folder's
`.env` as a fallback.

```
<data dir>/                       # ~/DepopSeller - the one folder a seller carries between machines
  product_image/<batch>/          # any safe folder name: a date, "Autumn knits", ...
    raw_image/      input HEIC — the app only ever *adds* files here (upload / import); existing photos are never modified, moved or deleted
    thumbs/         512 px JPEG cache (rebuilt on demand if missing)
    cache/          scan.json + cached model responses (generated)
    manifest.csv    one row per photo; the human-reviewed truth
    manifest.bak.csv  previous version, written by every save
    sort_image/     optional export: <item_id>_<photo_no>.jpg + manifest.csv — always copied, never moved
  depop_seller.db                 # local SQLite: items + photos per batch
  description_style.md            # the seller's own style, started from the app's template
  style_history/                  # previous versions of it
  .env                            # ANTHROPIC_API_KEY

<app folder>/                     # the software: code, launchers, the extension, the style template
```

## Step 1 pipeline

```
.venv\Scripts\python.exe -m depop_seller check                 # env, batches, API key status
.venv\Scripts\python.exe -m depop_seller sort <batch>          # scan -> group (API) -> manifest.csv
.venv\Scripts\python.exe -m depop_seller review <batch>        # drag-and-drop review UI in the browser; Approve = apply
.venv\Scripts\python.exe -m depop_seller sort <batch> --apply  # apply from the CLI instead: sort_image/ + DB
```

- `sort` reuses an existing `manifest.csv` (human edits are sacred; it only refreshes derived columns); `--regroup` re-runs the engine after backing the old manifest up as `manifest.bak-*.csv`. `--limit N` for cheap API testing (with `--regroup`).
- Grouping engine (`group.py`, orchestrated by `group_batch`): Anthropic API, `claude-opus-5` by default (`--model`, `--effort`). (1) Windowed pass: 8 thumbnails plus 2 context photos from the previous window, time gaps as text hints, structured output via `client.messages.parse(output_format=WindowResult)`; the model also returns `is_product` (false -> skipped). (2) Merge pass (`find_duplicates`): a catalog of every item's cover at 384 px (prompt-cached via `cache_control` on the last catalog block, chunks of 80) plus 8 query items per call; `Match` results with `high` confidence are merged by `apply_matches` (later item's photos appended), `medium` ones are written to `cache/suggestions.json` for the review page. Responses are cached in `cache/group/` and `cache/match/`; `PROMPT_VERSION` / `MATCH_PROMPT_VERSION` are part of the keys. The engine writes `cache/proposal_windows.csv` and `cache/proposal.csv` for `learn`. `--engine local` (time gap + colour distance) is the offline fallback and over-splits.
- `learn.py` / `depop learn <batch>` scores a proposal against the reviewed manifest (boundary precision/recall, stitched items, moves, drops) and `--test-merge-pass` re-runs and scores the merge pass. Measured on a real 438-photo batch: windowed pass 100%/100%; merge pass found 7/7 reviewer merges + 38 correct ones the reviewer missed (one medium false alarm: a bag that was a styling prop in another item's photos). Cost: merge pass ~$2 on Opus for 101 items. There is no fine-tuning: improving the engine means editing prompts and re-scoring with `learn`.
- Manifest model (`manifest.py`) is explicit: `item_id`, `photo_no`, `skip`, `deleted`, `view` per row. `deleted` = not for sale (implies skip; shown in the UI's Deleted section, restorable by drag; `raw_image/` is never touched). `unused()` excludes deleted rows. `normalize()` renumbers items densely by first photo and photos within each item, so by hand you just type the item number a photo belongs to (any unused number starts a new item). Skipped photos have item 0. Photo 1 of an item is Depop's cover; views are front/back/side/label/detail/flaw/other (Depop's slot order) and drive the UI's Auto-arrange. **The photo order (`photo_no`) is chosen by the reviewer and is sacred**: nothing downstream may re-sort it — `sort` (reuse path), `--apply`, the DB, `sort_image` names and the future Depop upload all follow `photo_no` exactly. In the UI only the explicit Auto-arrange buttons reorder (the global one asks for confirmation); Trim to 8 removes photos but keeps the remaining order.
- Review UI (`review.py` + `static/review.html`): stdlib `ThreadingHTTPServer` on 127.0.0.1, one `ReviewServer` holding a `ReviewSession` per batch; every batch route takes `?batch=`. Routes: `/batches`, `/state`, `/save`, `/group` + `/group/status` (scan + Claude grouping in a background thread, for batches without a manifest — the page shows a "Group with Claude (about $x)" panel using `group.COST_PER_PHOTO`), `/apply` + `/apply/status`, `/thumbs/<file>` and `/large/<file>` (both rebuilt from the original on first request - into `thumbs/` and `cache/large/` - so a batch folder copied from another computer, or one trimmed to save space, still shows its photos instead of broken tiles). Vanilla-JS page: batch dropdown in the header, HTML5 drag and drop, per-card Merge into #, Auto-arrange, Delete item, Trim to 8 (burst duplicates and lowest-priority views go to Unused), a "Possible re-shoots" panel fed by `/suggestions` (Merge / Not the same → `/suggestions/dismiss`), Unused bin and a Delete drop zone (Deleted section at the bottom), a ✕ on every tile (delete) / ↩ in the Deleted section (restore to Unused), a lightbox on image click (arrow keys, Esc, Delete/Unused buttons), Save (writes manifest.csv + manifest.bak.csv; payload = items / unused / deleted / views), Approve (apply, polled). `save()` validates the whole payload before mutating rows and refuses (409) when manifest.csv changed on disk since the session loaded it; `ReviewServer.session()` reloads a session whose manifest changed on disk. Synthetic mouse drags from browser automation don't start native DnD — test the handlers with dispatched `DragEvent`s and leave real drags to a human. `window.confirm` can be overridden in automation to click the paid buttons.
- Selling, preferred path (`chrome_extension/` + `static/sell.html`): a Manifest V3 extension the user loads unpacked. `sell_page.js` runs on 127.0.0.1:8765, marks `documentElement.dataset.depopSellerExt` and stores `{batch, item, server}` in `chrome.storage.local` on a `depop-seller:open` postMessage; the page then opens `https://www.depop.com/products/create/` in a new tab. `depop.js` runs on depop.com, polls for a pending job + the create page + `input[type=file]`, fetches `/sell/photos` (JSON of `{name, url}` in reviewer order, max 8; the server converts to 2048 px JPEGs first) and the images, builds a `DataTransfer`, sets `input.files` and dispatches input/change (one per slot if the input is not `multiple`), shows a banner, clears the job, POSTs status "opened". The server sends `Access-Control-Allow-Origin: *` and answers OPTIONS so depop.com can call it. This runs in the user's own logged-in Chrome — no automation flags — because Depop's bot protection 403-blocked the Playwright window on its second run (2026-09-19). Test the content script with the harness pattern in git history: inject it into `/sell/testform` with a `chrome.storage` shim.
- Descriptions (`describe.py`, routes `/sell/describe` + `/sell/describe/status`) run **only on the user's Claude subscription through the Claude Code CLI — the Anthropic API must never be used for descriptions** (user's rule: the API is for photo grouping only; the API engine was removed on 2026-09-20). `draft_description` builds one prompt (system rules + the whole `description_style.md` + the facts line + the paths of the cover and up to 3 label/detail/flaw close-ups from `cache/large/`, which the CLI reads itself with the Read tool) and `run_claude_code` runs the desktop app's bundled CLI (found by `find_claude_cli`: `DEPOP_CLAUDE_CLI`, PATH, `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude\claude-code\<ver>\claude.exe` — the packaged app's real files; `%APPDATA%\Claude\...` is only visible inside the app's own processes) as `claude -p --output-format stream-json --verbose --allowedTools Read --max-turns 12 --model opus` with the whole prompt on **stdin** (command-line length limits; fed from a thread, stderr drained by a thread). **Billing guarantee, two layers:** (1) the CLI gets `subscription_env()` — the parent environment minus every `ANTHROPIC_*` variable (until 2026-09-20 `load_api_key()` exported the grouping key into `os.environ` via `load_dotenv`, the CLI inherited it and silently billed the API instead of the subscription — ~$0.66 lost; `load_api_key()` now reads `.env` with `dotenv_values` without exporting, and `group.py` passes `api_key=` explicitly); (2) the first `system/init` event's `apiKeySource` must be `none`, otherwise `BillingRefused` and `_kill_tree` (taskkill /T on Windows — a `.cmd` shim would survive `Popen.kill()`). `DraftResult.credential` records the source; `Draft` = text + title/brand/size/color/condition/measurements/category_hint/missing/tip, parsed from the `result` event (`_extract_json` handles fences); cost is None. The CLI has its own login separate from the desktop app: the user signs in once from Settings → **Sign in with Claude** (in the browser, see the Settings bullet); until then the CLI answers "Not logged in". `find_claude_cli` searches, in order: `DEPOP_CLAUDE_CLI`, PATH, the desktop app's bundle dirs per OS (`_bundle_dirs`: the packaged-app path on Windows, `~/Library/Application Support/Claude/claude-code` on macOS), then standalone installs (`_standalone_paths`: `~/.claude/local`, homebrew, npm) - PATH is never relied on because an app launched from Finder or Explorer inherits a minimal one. `_kill_tree` uses `taskkill /T` on Windows and `killpg` elsewhere (the CLI gets `start_new_session=True`). `ReviewServer.start_describe(batch, item_ids, facts)` runs items sequentially in a thread, saves text + fields to the DB (`items.facts` / `items.measurements` added by `db._migrate`), state in `describe_state[batch][item]`, and `_log_draft` writes a readable `cache/drafts/item###_<ts>.txt` per draft. The Sell page has no engine choice and no cost figures; the card shows "Drafted with Claude Code". Note the CLI's `total_cost_usd` field is an estimate it always prints, not a charge. `/sell/photos` also returns `description`, and `depop.js` pastes it after the photos via `fillDescription`: tries textarea selectors, then visible `[contenteditable]` boxes (execCommand insertText, fallback textContent + InputEvent), then inputs; verifies the value took; the banner reports failure. Helper version is in the manifest (1.1) and mirrored as `HELPER_VERSION` in sell.html, which warns when Chrome still runs an older copy (unpacked extensions need a manual reload on chrome://extensions). Tested with a stub `.cmd` CLI speaking stream-json (`tests/test_claude_code_engine_parses_cli_envelope`, `test_claude_code_never_sees_the_api_key`). Gotcha that has now bitten twice: the Bash tool turns `\n` inside heredocs into real newlines - write files with escapes through the Write tool or build strings with chr(10). In a page's JavaScript a real newline inside a quoted string makes the whole `<script>` fail to parse, and the page then sits there with every status still reading "checking..." while the server answers fine; `test_every_page_script_has_no_string_broken_across_lines` catches that now. Test code has the same trap - build regex escapes with `chr(92)`.
- Sell page (`static/sell.html`, routes `/sell/state`, `/sell/item`, `/sell/reorder`): cards in manifest order with unlisted items first and listed ones under a "Listed on Depop" divider at the bottom (ticking Listed re-renders and moves the card); the red button is labelled just "Depop". Photo tiles are draggable **within their own item only** (regrouping stays on the review page): drop → `POST /sell/reorder?item=N {seqs:[...]}` → `ReviewSession.reorder_item` sets `photo_no`, writes manifest.csv + manifest.bak.csv through the same `_check_unchanged` (409) / `_write_manifest` helpers as `save()` (so an open review window with unsaved edits will get the 409 on its next Save — by design), and the page re-renders just that card from the response. `normalize()` orders items by their smallest `seq`, so reordering never renumbers items and the DB keeps the item's fields (same photo set). Clicking a tile opens a lightbox (thumb first, then `/large/`; arrows/Esc; "Make cover" = reorder with that photo first). Sell-state photos carry `seq` for this. Handlers are tested with dispatched `DragEvent`s in the browser (see the review-page note) and `test_sell_reorder_writes_manifest_and_keeps_item_fields`.
- Selling, fallback path (`listing.py`, routes `/sell`, `/sell/state`, `/sell/open`, `/sell/status`, `/sell/item`): `Lister` is a queue processed by one worker thread that owns a Playwright persistent context — the installed Google Chrome (`channel="chrome"`, falling back to msedge / bundled chromium) with its own profile in `.chrome-profile/` so the Depop login persists. A job converts the item's first 8 photos via `ReviewSession.large_image` (2048 px JPEGs in `cache/large/`), opens `https://www.depop.com/products/create/` in a new tab, waits up to 15 min for `input[type=file]` (login by the human), uploads all files at once when the input is `multiple` else one per slot, fills a textarea with the description if any, and leaves the tab open. **It never presses Post.** `db.sync_from_manifest` mirrors the manifest into the DB on every `/sell/state`, keeping status/description/depop_url per item (by photo set). `/sell/testform` is a stand-in form for smoke-testing the upload code without Depop. Playwright's sync API must stay on the worker thread. `sort --apply` / `sort_image` is now optional (export only).
- Hub / batches page (`static/hub.html`, the app's home): one card per batch with its cover (`GET /batches/cover`, a 512 px JPEG made on demand into `cache/cover-<stem>.jpg`), counts, `updated`, and the buttons **Add photos**, **Import folder…**, **Group with Claude (about $x)**, **Review**, **Sell**, **Rename**, **Open folder**. Photos go in from the app: drag and drop onto a card or the new-batch zone, or the file picker, uploading each file with `POST /batches/photos?batch=&name=` (raw body, three at a time, progress bar; never overwrites unless `replace=1`), or `POST /batches/import {folder}` which copies every photo from a folder on this computer (originals untouched). Grouping runs from the card (`POST /group` + `/group/status`) and jumps to the review page when it finishes. **Batch names are free text** (`safe_batch_name`: no `\ / : * ? " < > |`, no leading dot, no trailing dot, not a Windows reserved name, ≤60 chars) - `config.batch_dirs()` orders batches by `raw_image` mtime, so "newest" means most recently used, not alphabetically last. `POST /batches/rename` renames the folder and the `items`/`photos` rows in the DB (refused while a group or apply job is running). Uploaded names go through `safe_photo_name` (basename only, picture extension only).
- **CORS is limited to the extension's needs**: `DEPOP_ORIGINS` × `CORS_PATHS` (`/sell/photos`, `/sell/item`, `/large/`) - any other origin gets no `Access-Control-Allow-Origin`, `OPTIONS` elsewhere is 403, and every POST with a foreign `Origin` is refused (`_foreign_origin`). Without this, any page open in the seller's browser could drive the server, which now writes files. Covered by `test_only_depop_gets_cors_and_other_sites_cannot_post`.
- **Design system** (`static/app.css`, served at `/app.css`, linked first by every page): warm linen neutrals, a single blue `--primary` for actions (the sellers asked for blue generate buttons), `--depop` red for the Depop button, serif `--font-display` for the wordmark and titles, system sans for everything else - no web fonts, since the only network calls allowed are Anthropic and Depop. Pages keep only their own layout in `<style>` and must use tokens, never a colour or a `:root`; the short legacy names (`--blue`, `--card`, `--green`, `--red`, `--amber`) alias the tokens. No `background-attachment: fixed` - it repaints the whole background on every scroll frame and made long Sell pages stutter. `test_every_page_uses_the_shared_design` guards the link and the no-palette rule.
- **Sell page selection**: a checkbox per card plus Select → All / Without a description / None, and **Generate Selected Descriptions** (blue, sticky header, shows the count) posting the ticked ids with each card's current facts to `/sell/describe`; the per-item button is **Generate Description**. Ticks live in the `SELECTED` set, not the DOM, because cards are redrawn. While descriptions are being written, `refresh()` redraws **only cards whose `snapshot()` changed and never one containing `document.activeElement`** (a skipped card catches up on a later tick once the cursor leaves it); `render()` only when a card changes listed/unlisted, since that moves cards. A full redraw every 2.5 s used to wipe whatever the seller was typing in another card.
- **No console windows, ever**: the app runs windowless, so Windows hands every console program it starts a window of its own - that was the black Windows Terminal box on Generate Description. `desktop.no_console()` (`CREATE_NO_WINDOW`) goes on every background `Popen`/`run`: Claude Code, `taskkill`, the icon-restoring PowerShell. The fallback sign-in terminal (offered only after a browser sign-in fails) is meant to be seen and is the only exception. Verified against a control run without the flag, which did open a Windows Terminal window; `test_background_programs_start_without_a_console_window` pins it.
- **One app, three tabs.** All three pages carry the same header: the icon + "Depop Seller" (links to `/hub`) and `nav.tabs` with **Batches** (`/hub`) / **Review** (`/`) / **Sell** (`/sell`). `syncTabs(active, batch, hasManifest)` - a copy in each page, they share no JS - marks the active tab, carries `?batch=` across, and greys out (`.off`) what does not apply yet. Window titles are `Depop Seller`, `Depop Seller – Review <batch>` (with `*` when unsaved), `Depop Seller – Sell`. There is exactly **one launcher per OS**: `Depop Seller.cmd` and `Depop Seller.app`, both opening the hub. Neither may be moved out of the project folder (they resolve `.venv` relative to themselves): Windows gets a Desktop shortcut from `make_desktop_icon.ps1`, and `desktop.ensure_desktop_shortcut()` re-runs it from `cli.main` whenever the shortcut is gone - setup is skipped entirely when a `.venv` already exists, so a failed or skipped icon step would otherwise leave no way into the app. The Desktop folder comes from `User Shell Folders` in the registry, because OneDrive's folder backup moves it out of the home directory. It (WScript.Shell, `static/icon.ico`, `WindowStyle = 7` so the console starts minimised), and the macOS bundle falls back to the project path `setup.sh` records in `~/Library/Application Support/Depop Seller/project-path`, so a copy of the `.app` on the Desktop or in /Applications still works (`claude_login.cmd` / `claude-login.sh` stay for the one-time sign-in). `product_image.cmd`, `review.cmd` and `sell.cmd` were removed on 2026-09-23 - do not reintroduce per-page launchers, use the tabs. An installed copy (`config.bundled_runtime()`: the running Python is `runtime\` next to the app folder) skips `ensure_desktop_shortcut` - the installer owns its icons, and one the user deleted stays deleted - and `Depop Seller.cmd` inside it just starts `..\runtime\pythonw.exe`, never setup.
- **First run installs itself.** Neither user is an engineer, so setup must not need a terminal: `Depop Seller.cmd` and `Depop Seller.app/Contents/MacOS/depop-seller` both check for `.venv` and, when it is missing, run `setup.ps1` / `setup.sh` themselves, then start the app (Windows also gets the Desktop icon, then `pause` so the message can be read - `timeout` fails whenever stdin is not a console). The macOS bundle probes python3.14→3.12→python3 for >= 3.12 and, if none qualifies, offers to open python.org rather than failing; progress is `display notification`, failures are dialogs pointing at `~/Library/Logs/Depop Seller.log`. Rehearsed on a recipient-shaped copy (no `.venv`, no photos, no `.env`) - it installed and launched; remember that `setup.ps1` rewrites the Desktop shortcut, so re-run `make_desktop_icon.ps1` afterwards. **Gatekeeper is the one thing left**: an unsigned `.app` that arrived as a download is blocked until the user allows it in System Settings → Privacy & Security; copying the folder from a USB stick or a synced drive carries no quarantine and avoids it.
- **Windows installer** (`installer.py`, `installer/DepopSeller.iss`, built by `release`): `DepopSellerSetup.exe` (about 23 MB) installs per user - `PrivilegesRequired=lowest`, no administrator password - into `%LOCALAPPDATA%\Programs\Depop Seller` as `runtime\` (Python's official **embeddable** build for the release machine's exact Python, downloaded once from python.org into `build/`, with a `python3XX._pth` of `python3XX.zip`, `.`, `Lib\site-packages`, `..\app`, `import site` - so it ignores every other Python on the machine) and `app\` (the release zip unpacked - the folder the updater keeps current). Libraries are `pip install --target` with **every package of the build venv as a constraint**, so the bundle has exactly the versions the tests passed with. `smoke_test` imports everything from the staged runtime (and checks the modules came from the bundle) and starts the staged app's server, asks `/version`, then `/quit`; `check_path_lengths` fails the build if a file would pass 260 characters once installed (`MAX_INSIDE`: the anthropic SDK's longest compiled type is ~159). Start menu + Desktop icons run `runtime\pythonw.exe -m depop_seller hub` in `app\`; `[InstallDelete]` wipes both folders so an upgrade starts clean; `PrepareToInstall` and `InitializeUninstall` POST `/quit` to 127.0.0.1:8765 so an open copy lets go of its files. **Never change `AppId`** - it is how a newer installer upgrades instead of adding a second copy. Unsigned, so SmartScreen says "Windows protected your PC" once (More info → Run anyway); the README says so. Inno Setup 6 is on the release machine per-user (`%LOCALAPPDATA%\Programs\Inno Setup 6`, found by `find_iscc`, or `DEPOP_ISCC`). **Testing an installer on a working machine**: `/VERYSILENT /SUPPRESSMSGBOXES /desktopicon=no` (the icon would otherwise replace the developer's own `Depop Seller.lnk`), only with nothing on port 8765 (it would be closed), never into a deep folder (the 260 limit - a long temp folder is enough to break it), and uninstall afterwards with `unins000.exe /VERYSILENT`. - **Giving the app away**: Settings shows the project page link first (the page has the Download button); the zip is the fallback for no internet. **The zip** (`share.py`, `POST /settings/share`) writes `~/Desktop/Depop Seller <date>.zip` containing the project minus `SKIP_DIRS` (`.git`, `.venv`, `product_image`, `style_history`, `.chrome-profile`, `.claude`, caches, `*.egg-info`), minus `.db` / `.log` / `.pyc` / `.zip`, minus anything named `.env*`, plus a generated plain-language `START HERE.txt` (`GUIDE`; a copy that came out of a zip already holds one, so `_included` leaves the folder's copy out - but `is_shareable` still accepts it, since every release carries one; skipping it there once made the updater refuse every release, and `test_the_app_folder_is_the_release_zip_unpacked_with_one_guide` pins both). Modes are set explicitly (`_add` builds each `ZipInfo` with `create_system = 3` and `0o755` for `Contents/MacOS/*` and `*.sh`, `0o644` otherwise): **Windows has no executable bit**, so a plain `ZipFile.write` ships an app bundle whose executable cannot be run, and macOS reports that as "you need to install Rosetta" - nothing to do with architecture. `Info.plist` also sets `LSRequiresNativeExecution`. Before writing, every chosen name is checked against `SECRET_MARKERS` and the whole thing is refused if one matches - the zip must never carry the owner's key, photos or listings. Recipients use **their own** API key and Claude account. `test_share_copy_carries_the_app_but_never_the_secrets` builds a fake project with a `.env`, a DB and photos in it and asserts exactly what does and does not travel.
- **No console for the people using it** (they are not engineers; a terminal window reads as something being wrong). The Windows Desktop shortcut runs `.venv\Scripts\pythonw.exe -m depop_seller hub` - **pythonw has no console at all**, which also means `sys.stdout`/`sys.stderr` are `None` and any `print` would raise: `cli.windowless()` detects that (or `DEPOP_QUIET=1`, set by the macOS bundle) and `_log_to_file()` redirects both to `config.LOG_FILE` (`%LOCALAPPDATA%\Depop Seller\app.log`, `~/Library/Logs/Depop Seller.log`) before anything prints. A startup failure with no console calls `alert()` (MessageBoxW / osascript) pointing at the log. **Closing the app window closes the app** (the user asked for no background process): every page sends `navigator.sendBeacon('/closing')` on `pagehide`, and `arm_close()` waits `CLOSE_GRACE_S` (10 s) before shutting down - cancelled if any request arrives afterwards, because moving between tabs also unloads a page, or if `busy()` reports a running group / describe / style / apply job or a Depop handoff within `HANDOFF_QUIET_S` (120 s, so the helper can still fetch `/sell/photos`). Do not use `visibilitychange` for this: minimising the window would look identical to closing it and nothing would arrive to cancel it. `POST /quit` still shuts the server down (`self.server.shutdown()` on a thread after answering) behind **Settings → Close Depop Seller**; foreign-origin POSTs are already refused. `Depop Seller.cmd` stays as the diagnostic launcher that shows the messages. Do not make the icon run a `.cmd` again - that is where the console came from. macOS parity (verified by reading, not by running - there is no Mac here): the bundle never opens Terminal, sets `DEPOP_QUIET=1`, logs to `~/Library/Logs`, and `Info.plist` sets **`LSMultipleInstancesAllowed`** because macOS otherwise just activates the running copy on a second double-click instead of reopening the window (with it, the second instance finds the port busy, opens the window and exits, like Windows). The sign-in `osascript` **must single-quote the CLI path** - it lives under "Application Support" - covered by `test_claude_sign_in_window_quotes_the_mac_path`. `setup.sh` clears `com.apple.quarantine` for copies that arrived as a ZIP.
- **Updating while the app runs.** The pages are read from disk on every request but the routes live in the running process, so after a `git pull` or an edit the browser shows new tabs that the old server answers with "not found". `GET /version` reports `stale` (`code_mtime()` - newest mtime across `depop_seller/*.py` and `static/*.html` - is newer than at startup); every page calls `checkVersion()` and shows `#stale-banner`, which carries a **Close it now** button (`POST /quit`) and then tells the user how to reopen - `/version` returns `platform` so the wording names the desktop icon or the Dock. Never word it as "close the console window": since the launcher went windowless there is no console to close. A server so old it has no `/version` route answers 404, which the pages also treat as stale. After adding a route, tell the user to restart the app.
- **Check for updates** (`updates.py`, Settings → Updates, routes `POST /updates/check`, `POST /updates/install`, `GET /updates/status`): `check()` asks `api.github.com/repos/doyoungp-dev/depop_seller/releases/latest` (stdlib `urllib`, User-Agent set, 20 s timeout) and never raises - 404 means nothing published yet, 403/429 rate limited, offline is a plain sentence. `/updates/install` re-asks GitHub itself (the download URL is never taken from the request) and runs `install()` in a thread, refused while `busy()`; an update in progress counts as busy, so closing the window cannot stop it half-way. `install()` touches the **app folder only**: the download must start with `DOWNLOAD_PREFIX` and stay under 50 MB, every zip member must sit under `depop_seller_app/`, contain no `..`, backslash, drive or absolute path, and pass `share.is_shareable` (so a release can never write `.venv`, `.git`, `.env*`, `product_image`, a `.db` or the seller's `description_style.md`), and it must carry a `__version__`. Only files whose bytes differ are written; each replaced file is copied first to `%LOCALAPPDATA%\Depop Seller\previous-version` (machine folder, not the data folder); then `finish()` reinstalls the package only if `project.dependencies` changed and proves the new code imports in a separate process of the same Python (`_app_python()`: the `.venv`'s, or the installer's runtime) - if anything fails, the old files are put back and new ones removed. An installed copy has no pip, so a release whose `project.dependencies` changed is refused there before anything is touched, with a message pointing at the new `DepopSellerSetup.exe` (which upgrades in place). It never deletes a file a release dropped. A git checkout is refused ("update it with git pull"), which is what the developer's own copy shows. Restart: on Windows the old copy spawns the `pythonw.exe` next to the Python it runs on (`.venv\Scripts` or `runtime`) as `-m depop_seller hub --no-browser --port <same> --wait-for-port 30` detached with `DEPOP_QUIET=1` and shuts down 1.5 s later; `serve()`'s `_bind()` retries until the port is free, and a copy started that way arms `arm_close(grace=60)` so it stops if no window reconnects. The page polls `/updates/status`, then `/version` until the `pid` changes, and loads `/settings?updated=X`. macOS (`can_restart()` false, the bundle script owns the server process): the app closes and says to reopen it. Rehearsed end to end on a sandbox install with its own `.venv` and a local fake of the GitHub API: 1.0.0 → 1.0.1 in about 4 s, only the 3 version files rewritten, new copy running as pythonw, and it closed with its window; rehearsed again inside a copy installed by `DepopSellerSetup.exe` (restarted on `runtime\pythonw.exe`, page reloaded to "Updated to version 1.0.1").
- Settings tab (`settings.py`, `static/settings.html`, routes `/settings` + `/settings/state|key|key/test|login|login/test`): the two credentials and where everything lives, so a new user never edits a file. **The key never leaves the server**: `state()` returns only `{set, hint: mask(key), source, editable}` (`mask` keeps 7+4 characters) and nothing is logged - `test_api_key_is_saved_to_env_and_never_handed_back` asserts the key is absent from `state()`. `save_api_key` rewrites only the `ANTHROPIC_API_KEY` line of `.env` (other lines survive, written via a `.env.part` temp file), and refuses anything that is not `sk-ant-…`; an `ANTHROPIC_API_KEY` in the real environment wins over the file, so the page shows `editable: false` and disables saving. `test_api_key` validates with `client.models.list(limit=4)` - authenticated, no tokens billed - and turns `AuthenticationError` / `PermissionDeniedError` / `APIConnectionError` into plain sentences. - Style tab (`style.py`, `static/style.html`, routes `/style` + `/style/state|save|instruct|status|restore`): the seller changes the house style from inside the app, either by editing the file in a textarea or by typing an instruction ("from now on ...") that `style.propose()` sends to Claude Code (`run_claude_code`, `max_turns=4`, subscription only - the same billing guarantee as drafts) with the current file; it returns `{markdown, summary, diff}` from a JSON reply, **writes nothing**, and the page shows the unified diff for the seller to accept or discard. `save_style` validates (>= `MIN_CHARS`, must still have Markdown headings) and keeps the previous version in gitignored `style_history/` (names are timestamped with a `-2` style suffix for the same second; `history()` and pruning order by **mtime**, not by name, or same-second versions come back in the wrong order). `restore()` is just another save, so going back is itself undoable. - Data quirks seen in real batches: a session often starts on a mannequin and moves to flat lays, where many shots are labels or details of items already photographed - the merge pass and the review page's Merge into # exist for that; a few frames are not products at all (a rack, a shelf, bedding); burst shots push some items past the 8-photo limit.
- `--apply` writes JPEG q90, long edge 2048 px, EXIF applied then stripped; refuses a non-empty `sort_image/` without `--force`; `db.replace_batch` carries item-level fields (description, status, ...) across re-applies when an item's photo set is unchanged.
- Known data quirks: timestamps alone cannot split items (within-item gaps overlap with between-item gaps); adjacent items can share a colour; burst shots share the same second and are near-duplicates the human drops during review. Depop allows 8 photos per listing; the UI flags larger items.

## Conventions

- Python: type hints, `pathlib`, `argparse` CLI, stdlib `logging`; small modules (`scan`, `group`, `manifest`, `review`, `apply`).
- Idempotent and safe: re-running never destroys data; `--apply` refuses to write into a non-empty `sort_image/` unless `--force`.
- Tests in `tests/` (pytest) use tiny synthetic images, never the real photos.
- Follow the Anthropic SDK patterns from the `claude-api` skill when touching `group.py` (no `budget_tokens`, no prefill; use `output_config` for structured output).
